Software Requirement Specification1. Overall Requirements1.1 Context DiagramThe Online Movie Ticket Booking System is a web-based software system designed to replace the traditional walk-in and phone-based processes for purchasing movie tickets, managing cinema operations, and tracking revenue at a single-branch cinema. The system enables customers to browse movies, select showtimes and seats, make online payments, and receive electronic tickets identified by a unique ticket code — all through a responsive web interface.The context diagram below illustrates the external entities and system interfaces for version 5.0. Five external actors and four external systems interact with it, each exchanging specific data flows:1.2 Main Business Processes1.2.1 Ticket Booking & PaymentLanes: Guest/Customer, System, Payment Gateway. Customer selects a movie and showtime, selects seats, optionally adds food and applies a promotion code, then pays; the System creates the invoice and tickets and shows the confirmation. (Maps to UC22-UC30) 1.2.2 Counter Sale & Ticket Check-inLanes: Walk-in Customer, Employee, System. A walk-in customer buys at the counter; the Employee selects the showtime/seats and collects payment, and the System creates the ticket and invoice. On the day of the show, the Employee looks up the ticket by code, email, or name and checks the customer in. (Maps to UC46-UC48)1.2.3 Movie → Schedule → Go-LiveLanes: Manager, System, Guest/Customer. The Manager adds a movie (optionally auto-filled from the TMDB API) and creates a showtime for it in a room; once the showtime is active the System publishes it, and the Guest/Customer can view and book it. (Maps to UC14, UC17, UC35, UC22)1.2.4 Promotion LifecycleLanes: Manager, System, Customer. The Manager creates a promotion code; the System activates it on its start date; the Customer applies the code at checkout; the System tracks the usage count; and the Manager deactivates, reactivates, extends, or deletes the promotion as it approaches or passes its end date. (Maps to UC42-UC43)1.2.5 Shift Scheduling & ExchangeLanes: Manager, Employee (requester), Employee (colleague), System/Notification. The Manager assigns an Employee to a shift; the Employee requests to exchange an upcoming shift with a colleague; the System notifies the colleague, who accepts or rejects; the System updates the shift assignment and notifies both parties. (Maps to UC53-UC55)1.2.6 Registration, Login & Password RecoveryLanes: Guest, System. The Guest registers an account (or signs in via Google OAuth), logs in, and if the password is forgotten, requests a reset link and sets a new password. (Maps to UC01-UC04)1.3 User Requirements1.3.1 Actors#ActorDescription1ManagerActors who have the highest rights in the system. The manager can manage all core modules including movies, genres, cinema rooms, schedules, food items, promotions, and employee accounts.2EmployeeStaff members who operate directly in the system. They can manage offline ticket selling, validate bookings (check-in via QR codes), and process food and beverage orders at the counter.3CustomerRegistered members of the system. In addition to guest features, customers can book tickets online, rate and review movies, manage their booking history, and update their personal profiles.4GuestUnregistered users who can operate the basic public functions of the system: view movie lists, view movie details, view promotions, check ticket prices and showtimes, and register for a new account.5System AdminActors responsible for high-level system administration and security. They manage all user accounts (including viewing the account list, blocking/unblocking, and assigning roles), configure system settings (such as banners, policies) and view System Logs to ensure integrity and compliance.  1.3.2 Use Cases (UC)The Online Movie Ticket Booking System defines 55 use cases organized into 5 functional groups, aligned with the actor inheritance hierarchy described in Section 1.3.1. Non-Functional Requirements3.1 External Interfaces3.1.1 User InterfacesThe web application shall provide a responsive user interface compatible with modern web browsers (Google Chrome, Mozilla Firefox, Microsoft Edge, Safari) on both desktop and mobile devices. The interface shall follow a consistent layout structure: a navigation bar on top, a main content area in the center, and a footer at the bottom. All pages must be rendered in Vietnamese as the default language. Admin/Manager/Employee dashboards use a sidebar navigation layout for management functions.3.1.2 Hardware InterfacesThe system shall interface with the following hardware components:QR code lookup form (search by ticket code, email, or name) for ticket check-in at the counter (UC-46). No physical scanner or camera is used.Ticket printer at the counter for manual ticket creation (UC-48).Standard input devices (keyboard, mouse, touchscreen) for all user interactions.3.1.3 Software InterfacesThe system shall integrate with the following external software services:Payment Gateway: VNPay, MoMo, or ZaloPay API for online payment processing (UC-27).Email Service (SMTP): For account registration confirmation, password reset, and booking confirmation emails.Database: Microsoft SQL Server for data storage and retrieval.Web Server: Apache Tomcat running Java Servlet/JSP application.3.1.4 Communication InterfacesThe system shall communicate over HTTPS (TLS 1.2 or higher) for all client-server interactions. RESTful API endpoints shall be used for payment gateway integration. Email communication shall use SMTP over port 587 with TLS encryption.3.2 Quality Attributes3.2.1 UsabilityUSR-01: A new customer shall be able to complete the full ticket booking flow (select movie → select showtime → select seat → pay) within 5 minutes without prior training.USR-02: The system shall display clear error messages in Vietnamese when the user provides invalid input, indicating the exact field and expected format.USR-03: Navigation between major functions shall require no more than 3 clicks from the home page.USR-04: The seat selection map shall use intuitive color coding: available (green), occupied (red), selected (blue), VIP (gold border).USR-05: All management pages (Manager/Employee dashboards) shall include search, filter, and sort capabilities on list views.USR-06: The system shall be responsive and usable on screen widths from 375px (mobile) to 1920px (desktop).3.2.2 PerformancePER-01: Page load time shall not exceed 3 seconds under normal conditions (≤ 100 concurrent users).PER-02: The seat availability map for a showtime shall load within 2 seconds, including real-time occupancy status.PER-03: Ticket lookup and check-in verification (UC-46) shall return the result within 1 second to avoid customer queues.PER-04: Payment processing (UC-27) shall complete within 15 seconds, including gateway response time. If timeout occurs, the system shall automatically mark the invoice as "Failed."PER-05: Revenue statistics reports (UC-49) shall be generated within 5 seconds for a date range of up to 1 year.PER-06: The system shall support at least 200 concurrent users during peak hours (e.g., weekend evenings, movie premiere events).3.2.3 SecuritySEC-01: All user passwords shall be stored using a one-way hashing algorithm (bcrypt or SHA-256 with salt). Plain-text passwords shall never be stored or logged.SEC-02: The system shall enforce role-based access control (RBAC) with 5 roles: Guest, Customer, Employee, Manager, and System Admin. Each API endpoint and page shall verify the user's role before granting access.SEC-03: User sessions shall expire after 30 minutes of inactivity. The system shall force re-authentication after session timeout.SEC-04: The system shall prevent common web vulnerabilities including SQL Injection, Cross-Site Scripting (XSS), and Cross-Site Request Forgery (CSRF).SEC-05: All sensitive actions (account deletion, role assignment, system configuration changes) shall be recorded in the SystemLog table with the actor's AccountID, action type, IP address, and timestamp.SEC-06: Failed login attempts shall be limited to 5 within a 15-minute window. After exceeding this limit, the account shall be temporarily locked for 30 minutes.3.2.4 Reliability & AvailabilityREL-01: The system shall have a minimum uptime of 99% during operating hours (8:00 AM – 12:00 AM daily).REL-02: In case of a payment gateway failure, the system shall allow the customer to retry payment or switch to a different payment method without losing the selected seats for up to 10 minutes (seat hold mechanism).REL-03: The database shall be backed up daily. ⚠ Not implemented in the current codebase: there is no backup/restore action anywhere in AdminServlet or elsewhere; this remains a planned requirement.REL-04: The system shall gracefully handle unexpected errors by displaying a user-friendly error page instead of exposing stack traces or system internals.3.2.5 ScalabilitySCA-01: The database schema shall support adding new room types (e.g., ScreenX, Dolby Atmos) without modifying existing table structures (currently enforced via CHECK constraint on Room.RoomType).SCA-02: The system shall support adding new payment methods (e.g., Apple Pay, bank transfer) by extending the PaymentMethod field without requiring database schema migration.SCA-03: The system architecture shall allow horizontal scaling of the web server behind a load balancer for future growth.3.2.6 MaintainabilityMAI-01: The application shall follow the MVC (Model-View-Controller) architecture pattern to separate concerns between data access, business logic, and presentation.MAI-02: All system configuration values (banner images, policy text, theme settings) shall be stored in the database and manageable through the admin UI (UC-50) without requiring code deployment.MAI-03: The system shall maintain comprehensive audit logs in the SystemLog table for all critical operations, supporting troubleshooting and compliance auditing. 5.
